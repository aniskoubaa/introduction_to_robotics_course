Code · heading ↔ quaternion, both directions

ee414_course/quaternion_demo.pylines 24–34

def quat_from_yaw(theta):
    """A rotation about z only -- the only kind a floor robot ever has."""
    return (0.0, 0.0, math.sin(theta / 2.0), math.cos(theta / 2.0))


def yaw_from_quat(x, y, z, w):
    """Pull the heading back out. This is what tf2 does at the edges."""
    siny_cosp = 2.0 * (w * z + x * y)
    cosy_cosp = 1.0 - 2.0 * (y * y + z * z)
    return math.atan2(siny_cosp, cosy_cosp)

A floor robot only ever rotates about z, so two of the four numbers are always zero. yaw_from_quat is what tf2 runs at every edge of the tree.

The argument

A 3×3 matrix drifts too, but its constraint is six conditions — repair means Gram-Schmidt or an SVD. tf2 stores quaternions because the cheap repair is the one you can afford every cycle.

def resolve_twist_type(node, topic, timeout=3.0):
    """Return the message class `topic` carries, or Twist if nobody says. ..."""
    topic = topic if topic.startswith("/") else "/" + topic
    deadline = time.monotonic() + timeout

    while time.monotonic() < deadline:
        for name, types in node.get_topic_names_and_types():
            if name == topic and types:
                if "geometry_msgs/msg/TwistStamped" in types:
                    return TwistStamped
                if "geometry_msgs/msg/Twist" in types:
                    return Twist
        time.sleep(0.1)

    # Nothing is bound to the topic yet -- this is the turtlesim case, where
    # our publisher is the first one there. Twist is the right default.
    return Twist

def publish_raw(self, **fields):
    """Publish a Twist with arbitrary fields set, including useless ones."""
    if self.msg_type is TwistStamped:
        msg = TwistStamped()
        msg.header.stamp = self.get_clock().now().to_msg()
        twist = msg.twist
    else:
        msg = Twist()
        twist = msg

    for name, value in fields.items():
        part, axis = name.split("_")

Simple · forward kinematics, and nothing else

beginner_student_freindly/simple_kinematics.pylines 10–18

r = 0.033      # wheel radius, in metres        (TurtleBot 3 Burger)
L = 0.160      # distance between wheels, metres


def forward(wL, wR):
    """Wheel speeds in (rad/s)  ->  how the BODY moves."""
    v = r * (wR + wL) / 2      # forward speed, m/s
    w = r * (wR - wL) / L      # turn rate, rad/s
    return v, w

The two constants and the two equations, in nine lines. The sum of the wheel speeds produces forward motion; the difference produces rotation.

Code · forward kinematics — wheels to body

ee414_course/wheels_to_body.pylines 25–29

def forward_kinematics(w_left, w_right, r=WHEEL_RADIUS, L=WHEEL_SEPARATION):
    """Wheel angular speeds (rad/s) -> body (v, omega) in (m/s, rad/s)."""
    v = r * (w_right + w_left) / 2.0
    omega = r * (w_right - w_left) / L
    return v, omega

Two lines of arithmetic. The other ninety in the file are printing.

def inverse(v, w):
    """How the body should move  ->  the wheel speeds that do it."""
    wL = (v - w * L / 2) / r
    wR = (v + w * L / 2) / r
    return wL, wR

The same two equations solved the other way round, in the same file.

Code · inverse kinematics — body to wheels

ee414_course/body_to_wheels.pylines 28–32

def inverse_kinematics(v, omega, r=WHEEL_RADIUS, L=WHEEL_SEPARATION):
    """Body (v, omega) -> wheel angular speeds (w_left, w_right) in rad/s."""
    w_left = (v - omega * L / 2.0) / r
    w_right = (v + omega * L / 2.0) / r
    return w_left, w_right

The same two equations, solved the other way round. This is the direction a real robot works in: you ask for v and ω, the wheels are what it has.

Code · the two integrators, side by side

ee414_course/dead_reckoning.pylines 29–45

def step_euler(x, y, theta, v, omega, dt):
    """Pretend the heading is frozen for the whole timestep, then turn."""
    x += v * math.cos(theta) * dt
    y += v * math.sin(theta) * dt
    theta += omega * dt
    return x, y, theta


def step_exact_arc(x, y, theta, v, omega, dt):
    """Follow the arc the robot is actually on. Exact when v and omega are held."""
    if abs(omega) < 1e-9:
        return step_euler(x, y, theta, v, omega, dt)
    R = v / omega                       # radius of the arc
    theta_new = theta + omega * dt
    x += R * (math.sin(theta_new) - math.sin(theta))
    y -= R * (math.cos(theta_new) - math.cos(theta))
    return x, y, theta_new

Euler freezes the heading for the whole step, then turns. The arc form follows the circle the robot is genuinely on, and is exact whenever v and ω are held constant — which, between two /cmd_vel messages, they are.

Two things

One: halve the timestep, halve the Euler error — first order, never zero. Two: the arc is 1e-16 at every timestep, because holding v and ω constant is an arc. At 0.05 s Euler is already 1.8 cm out on one quarter turn.

        print(f"  x={msg.x:6.3f}   y={msg.y:6.3f}   "
              f"theta={msg.theta:+.3f} rad = {math.degrees(msg.theta):+7.1f} deg")

A node, a subscription, a callback. Every subscriber follows these three steps in this order.

Do not skip this

Both estimates start 1.6 cm out and stay there. That centimetre and a half is the robot — the acceleration ramp, slip, mass — and no integrator removes any of it. It is the answer to "why not just integrate more carefully?".

The methods do separate, and by less than you would guess: over the half circle Euler holds at about 13 mm while the arc falls to 6 mm. Worth one sentence — at 20 Hz a step turns 0.02 rad, so the method is a millimetre-scale correction on a centimetre-scale error. The recorded numbers came off a robot starting at the origin; start it elsewhere and the shared offset swamps the difference.

The Whole Idea in One Line

Scroll up to any drive run and point at one line: straight: 2.0 m at 1.0 m/s -> hold for 2.000 s. That division is the definition.

Then the closing question, which is Week 5's opening one: the node already knows where it is. Why did it not use that?

Simple · open loop, in fifteen lines

beginner_student_freindly/simple_move.pylines 43–57

seconds = DISTANCE / SPEED            # <-- THE ENTIRE CONTROL LAW
print(f"\n  {DISTANCE} m at {SPEED} m/s  ->  hold for {seconds:.2f} s\n")

msg = Twist()
msg.linear.x = SPEED

try:
    deadline = time.time() + seconds
    while time.time() < deadline:
        pub.publish(msg)              # a topic does not latch: keep sending
        time.sleep(0.05)
except KeyboardInterrupt:
    pass
finally:
    stop(pub)

seconds = DISTANCE / SPEED is the whole control law. No line below it reads the pose. That is the definition of open loop.

Code · the whole of open loop

ee414_course/drive.pylines 64–78

def send_for(self, v, omega, seconds):
    """Hold one Twist for a fixed time. This is the whole of open loop. ..."""
    period = 1.0 / self.rate_hz
    deadline = time.monotonic() + seconds
    while time.monotonic() < deadline and not graceful.interrupted():
        self.pub.publish(v, omega)
        rclpy.spin_once(self, timeout_sec=0.0)   # drain callbacks, never block
        time.sleep(period)
    self.stop()

Publish, wait, stop. The pose IS subscribed to, but only to report the error at the end — never to decide anything.

Simple · closed loop, in the same shape

beginner_student_freindly/simple_go_to_goal.pylines 52–75

def control(self):
    if self.pose is None or self.arrived:
        return

    # ---- THE CLOSED LOOP: three lines, and all of them LOOK ----------
    dx = GOAL_X - self.pose.x
    dy = GOAL_Y - self.pose.y
    distance = math.hypot(dx, dy)
    heading_error = normalize(math.atan2(dy, dx) - self.pose.theta)
    # ------------------------------------------------------------------

    if distance < TOLERANCE:
        self.pub.publish(Twist())
        print(f"\n  Arrived. {distance:.3f} m from the goal.")
        print("  It got here by looking, not by timing.\n")
        self.arrived = True
        return

    msg = Twist()
    msg.angular.z = clamp(K_ANGULAR * heading_error, MAX_W)   # P controller
    # Turn first if badly aimed, otherwise the two errors fight.
    if abs(heading_error) < math.radians(20):
        msg.linear.x = clamp(K_LINEAR * distance, MAX_V)
    self.pub.publish(msg)

Four lines compute the error from the most recent pose; the next two convert it into a velocity. That is the only difference from the program below.

Code · the same problem, closed loop

ee414_course/go_to_goal.pylines 91–119

while time.monotonic() < deadline and not graceful.interrupted():
    rclpy.spin_once(self, timeout_sec=0.05)
    pose = self.driver.pose

    # ---- THE CLOSED LOOP: look, then decide ----------------------
    distance = pose.distance_to(self.goal)
    heading_to_goal = pose.angle_to(self.goal)
    heading_error = normalize_angle(heading_to_goal - pose.theta)

    # ...

    omega = self.clamp(self.k_angular * heading_error, self.limits["w"])

    # Turn first if badly misaligned; otherwise a big heading error and
    # a big distance error fight, and the robot swings out on a curve.
    if abs(heading_error) > math.radians(20.0):
        v = 0.0
    else:
        v = self.clamp(self.k_linear * distance, self.limits["v"])

    self.driver.publish(v, omega)

Read the pose, work out the error, act on it, repeat. No duration is computed in advance. Put this beside the snapshot above: the difference between them is Week 5.

The one-line difference

Everything else computes duration = distance / speed once and hopes. This computes error = goal − where_I_actually_am fifty times a second.

Fixes

Every row was hit while preparing this sheet, on this machine.

A

The robot does not move and there is no error. ros2 topic type /cmd_vel. Jazzy's TurtleBot 3 bridge wants TwistStamped; a Twist publisher connects to nothing, silently.

B

No module named 'rclpy._rclpy_pybind11'. Anaconda's python3 is in front of the system one. conda deactivate, then check which python3 says /usr/bin/python3. ros2 run is unaffected — only python3 script.py, which is what a student types.

C

symbol lookup error … /snap/core20/… starting turtlesim, RViz2 or Gazebo. The culprit is LOCPATH (also GTK_PATH, GTK_EXE_PREFIX) pointing into /snap/code/.

Already fixed on this machine by a block at the end of ~/.bashrc that strips them — interactive shells only. For bash -c, source shared/screenshots/rosenv.sh.

D

Package not found. The workspace is not sourced in this terminal. Every terminal, every time.

E

RViz2 opens empty. Set Displays → RobotModel → Description Topic to /robot_description, or restart the launch file.

F

Gazebo slow, or the square badly wrong. Check the real-time factor. Well below 1.0 means timed durations no longer match distances — a real open-loop failure, but not the one you are teaching. Reduce speeds, or use turtlesim.

G

A node prints nothing when redirected to a file. Python buffers stdout. Prefix PYTHONUNBUFFERED=1. Affects recording, not live teaching.

H

The turtle drives off on its own, or a demo's numbers are absurd. A ros2 topic pub -r 10 is still running in a terminal you have scrolled away from. It publishes for ever and nothing says so.

pgrep -af 'ros2 topic pub' names it. This is worth knowing because it does not look like itself: the symptom is a 2 m square closing 2.8 m out, or a "nothing moved" slide in which the turtle has plainly moved.

I

Ctrl-C is safe, and it stops the robot. Every node in both packages catches the interrupt itself: it publishes a zero Twist, prints its summary, and exits 0. No traceback. Stop any demonstration at any point.

If you ever do see RCLError: publisher's context is invalid, the node was killed some other way and the robot is still driving — ros2 topic pub --once a zero Twist, or restart the simulator.
